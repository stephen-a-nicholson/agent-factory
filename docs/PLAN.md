Done when: a deliberately bad system prompt causes evaluate to fail and the champion alias does not move. **Done, 2026-09-10**, against a real Databricks Free Edition workspace. Summary of what was built and every real bug found, in the order encountered:

**Vector search sync (the ingest-side bug carried in from phase 2).** Adding a third document (financial regs) and re-running `ingest_f1` did not update the vector search index: a `TRIGGERED` delta-sync pipeline does not resync on its own just because the source table changed or the (unchanged) index resource got redeployed. Fixed by adding `sync_vector_search_index()` to `src/ingest/documents.py`, called after every chunks write, with the index name threaded through as a new `--index-name` job parameter computed the same static-string way as `_deploy_agent_job_resource`'s existing workaround for the same circular-dependency problem (`_vector_search_index_name` in `factory/generate.py`). That surfaced a second, deeper bug: the sync then failed repeatedly with `DIFFERENT_DELTA_TABLE_READ_BY_STREAMING_SOURCE`, traced via `databricks pipelines list-pipeline-events` to the sync pipeline tracking its source table by internal Delta table UUID through a streaming checkpoint, which `write_delta_table`'s DROP+CREATE pattern changes on every run. Fixed with a new `overwrite_delta_table_in_place()` in `src/ingest/delta.py` (true `mode("overwrite")` on the existing table, preserving its UUID), used only for the chunks table, which has a downstream streaming consumer; structured tables still correctly use drop-and-recreate. Recovered the already-corrupted index by deleting and letting the bundle redeploy recreate it, then verified with a real `ingest_f1` run: `indexed_row_count: 296` (69 sporting + 181 technical + 46 financial), `ready: true`.

**`evaluate_<name>` job and `alerts`/`dashboards` resources.** Added `src/evaluate/rag.py` (MLflow GenAI evaluate against the domain's `rag.eval.judges`, mapped to `mlflow.genai.scorers` classes, each forced to `model="databricks"` to avoid defaulting to an unconfigured "openai" provider) and `src/agent/promote.py` (moves `champion` to the version aliased `candidate`). Wired as one job, `evaluate_<name>`, with `promote` task-dependent on `evaluate`: a Databricks job skips a task whose dependency failed, so a failed evaluate means promote never runs, no application-level gating needed. Added the `<name>_eval_regression` `AlertV2` resource (single `margin = MIN(score - threshold)` query over a `VALUES` table built from `rag.eval.promotion_threshold`, confirmed executing correctly against the real warehouse via the statement execution API both before and after real eval data existed) and the `<name>_observability` dashboard (three widgets: eval score history, latest scores, serving endpoint traffic from `system.serving.endpoint_usage`/`served_entities`, confirmed queryable on this Free Edition workspace; shape reverse-engineered from a real dashboard already in the workspace via `databricks lakeview get`, since there is no public JSON schema for `serialized_dashboard`).

**`domains/f1/eval/rag.jsonl`.** All 25 questions and their `expected_response` ground truth were sourced from the real, already-ingested `chunks` table content (queried directly via the SQL statement execution API) and the real structured tables (e.g. "Max Verstappen won 19 races in 2023", "Lando Norris scored 394 points in 2025"), not guessed, including the real Cost Cap figure (US$215,000,000) found in the financial regs.

**Real bug: `evaluate_<name>`'s environment was missing `databricks-ai-search`.** First real `evaluate_f1` run failed with `No module named 'databricks.ai_search'`: `src/evaluate/rag.py` loads the packaged `rag_agent` model to call `predict()`, so the retriever tool's `AISearchClient` import needs that package in the *evaluate* job's environment too, not just `deploy_agent_<name>`'s. Fixed by adding `databricks-ai-search` to `_rag_eval_job_resource`'s environment dependencies. The task-dependency gate itself worked correctly even during this failure: `promote` was skipped, confirming the mechanism before the first real content-quality run.

**Real bug: `RetrievalGroundedness` scored nothing at all, not just low.** With that dependency fixed, the next real run wrote `correctness/mean` and `relevance_to_query/mean` but no `retrieval_groundedness/mean` key at all. Cause: `mlflow.genai`'s retrieval scorers extract retrieval context straight from a `RETRIEVER`-typed span's captured return value, recognising only a list of dicts with a `page_content`/`content`/`text` key — `_call_retriever` in `src/agent/rag_agent.py` was returning a pre-joined formatted string instead. Fixed by having `_call_retriever` return the structured rows (`_similarity_search` no longer formats them) and moving the string formatting into `_run_tool`, which is what the LLM tool-call response actually needs. Documented as its own paragraph in DESIGN.md section 8 since it is a real MLflow tracing convention, not obvious from the API surface.

**Architectural finding, not a bug: combined questions structurally cap groundedness.** `RetrievalGroundedness` only checks a claim against the RETRIEVER span, never the Genie tool's. Inspecting real per-trace assessments (via the `/api/3.0/mlflow/traces/search` endpoint) showed every combined-category question that correctly cited both a Genie-derived stat and a regulation fact scored `groundedness: no` for the Genie half, even though both halves were independently correct (`correctness: yes` on the same traces). There is no per-category threshold in the domain.yml contract, so f1's `promotion_threshold` was set from a real baseline run (correctness 0.76, groundedness 0.80 measured) rather than an upfront guess: `correctness: 0.70`, `groundedness: 0.75`. Documented in both DESIGN.md section 8 and `domains/f1/domain.yml` itself.

**Real bug: `deploy_agent_<name>` updated the live serving endpoint before evaluation ever ran.** Found running the "done when" scenario itself: set a deliberately bad `system_prompt` ("never call any tool... make up a plausible-sounding article number and statistic"), ran `deploy_agent_f1` (registered version 10 as `candidate`), then `evaluate_f1`, which correctly failed (correctness 56-68% against the 70% threshold) and correctly skipped `promote` (`champion` alias stayed at version 9, the last good one). But the *serving endpoint* was already on version 10, because `deploy.py`'s `main()` called `update_serving_endpoint` unconditionally right after registering the candidate — directly contradicting DESIGN.md section 6's stated flow, "the serving endpoint alias is only moved after eval passes". Fixed by removing that call from `deploy.py`; only `promote.py` calls `update_serving_endpoint` now, gated by the same task dependency as the alias move. Verified the fix for real: reverted the system prompt, redeployed (registered version 11 as `candidate`, confirmed the endpoint stayed on version 10, unchanged), ran `evaluate_f1` (passed: correctness 72%, groundedness 87.5%, relevance 92%), and confirmed `promote` moved `champion` to 11 and the endpoint to 11 — both the failing and passing paths now independently verified end to end, including the endpoint state, not just the alias.

**One real bug found in the generator's own dependent code, and one in a hand-written eval question — both fixed:**

1. **`gates/rules/naming.py`'s `naming_convention` rule broke on the first multi-word domain name.** It checked `domain_name in resource_key.split("_")`, which can never match when the domain name itself contains an underscore (`uk_rail`): splitting `ingest_uk_rail` on `_` gives `["ingest", "uk", "rail"]`, and `"uk_rail"` is never one of those tokens. `uv run python -m gates.run --target dev` against the real two-domain bundle failed all 10 `uk_rail` resource keys with this false positive before the fix. Fixed with a word-boundary-aware substring match (`(?:^|_)name(?:_|$)`) instead of token splitting; added a regression test (`test_naming_convention_accepts_multi_word_domain_names`) so a future multi-word domain name can't reintroduce this. This is a gates bug, not a generator bug: every actual generated resource key (`ingest_uk_rail`, `uk_rail_genie`, `deploy_agent_uk_rail`, ...) was already correct.
2. **A hand-written Genie benchmark question was ambiguous and passed on a technicality.** "What is York station's main origin or destination station?" got Genie searching broadly and pulling in unrelated stations with "Yorkshire" in their name (`Bentley (South Yorkshire)`, `Clapham (North Yorkshire)`, ...), answering "Leeds" as the primary destination with "London Kings Cross" only mentioned in passing among "other notable stations" — which still satisfied the benchmark's substring-match grading, a false pass. Reworded the question to specify the exact station name and exclude Yorkshire-named stations explicitly; re-ran and got a genuine, unambiguous pass citing London Kings Cross directly. Not a factory bug (this is domain content, not generator code), but worth recording: a loose `answer_contains` substring match can pass a genuinely wrong or overbroad answer, the same risk documented for f1's own Genie instructions around "Lapped" vs DNF in phase 1.

Three real, load-bearing findings from actually running `databricks bundle init` against this repo, not assumed from documentation:

1. `template_dir: "."` (pointing the template at the repo root directly, which is what DESIGN.md's original phrasing, "live at the repo root alongside the working project", suggested) fails outright: `Error: open .: no such file or directory`, reproduced in an isolated minimal case, so it is a real CLI limitation, not something specific to this repo's size. Settled on the standard `template/` subdirectory convention instead.
2. **`databricks bundle init` does not support directory symlinks in a template tree at all** ("`Error: write .../linked_dir: copy_file_range: is a directory`"), confirmed in an isolated minimal case before touching the real template. File symlinks work fine and are correctly dereferenced into real files in the output (confirmed the same way). This is why `factory/build_template.py` walks every shared directory itself and links each file individually, rather than symlinking whole directories.
3. **Only a file whose name ends in `.tmpl` gets its *content* rendered** (and the suffix stripped); every other file is copied byte for byte, even one that happens to contain literal `{{...}}`. Found by a real run leaving an unrendered `name: {{.project_name}}` in the scaffolded `databricks.yml` when the destination file was plain `databricks.yml` instead of `databricks.yml.tmpl`.

One more real, minor finding: symlinking `.gitignore` into `template/{{.project_name}}/` made `git status` on *this* repo fail with `Too many levels of symbolic links`, even though the same symlink resolved correctly under `cat`/`realpath`. Not fully root-caused (git evidently treats a per-directory `.gitignore` specially in its own tree-walk in a way a plain file read does not); worked around by copying `.gitignore` directly instead of symlinking it, low risk of drift since it rarely changes.

End-to-end verification actually performed: `databricks bundle init .` (repo root, local path) with `--config-file` supplying real answers, into a scratch directory; confirmed no symlinks and no stray `.tmpl` suffixes remained in the output, `domain.yml`'s `name:` and `databricks.yml`'s `name:` both correctly rendered; then, inside that scaffolded copy, ran `uv sync`, `uv run ruff check .`, `uv run pytest` (128 passed, same as the real repo), `uv run python -m factory.generate`, and `databricks bundle validate -t dev` against the real dev workspace (a genuinely separate bundle deploy path, `.bundle/my-agent-factory/dev`, not colliding with the real repo's own `.bundle/agent-factory/dev`) — all passed for real. The generator originally declared a `model_serving_endpoints` bundle resource per DESIGN.md's plan, and it genuinely could not be deployed: a real `bundle deploy` hit a circular dependency where the endpoint needed the domain's `rag_agent` model to already exist (it doesn't, until `deploy_agent_<name>` runs), and the job's own parameters referenced the endpoint's resolved name, so *creating the job resource* also depended on the endpoint having already deployed.
